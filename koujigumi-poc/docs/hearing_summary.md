## 積算業務の重要ポイント

### 1. 時間感

- 読み取り+拾い出しで**1案件10日〜2週間**
- 従来想定の「数日〜1週間」より長い
- 顧客から「2週間で概算を」と求められるが、**過去実績の手作業では間に合わない**

### 2. 最大の期待ポイント

> 「基本設計段階で建物用途・スパン等から原単位を推定して概算を出す」

- 詳細設計の詳細積算ではなく、**基本設計段階での概算**が主軸
- 構造図が整う前の段階で、AIが推測値を提示することが特に求められている
- 用途（工場/倉庫/事務所等）、構造、スパンがわかれば、経験則で配筋量や部材大きさを推定できる

### 3. 図面の実態

- 基本設計段階はPDFまたはスキャン画像が多い
- 構造図・設備図が未確定のケース多数
- 民間の設計事務所は図面品質にばらつきあり
- 官公庁案件はデータが整っている

### 4. 属人化と暗黙知

- ベテランが「図面に書いていない情報を想像して金額を出す」
- ベテランの「原単位の感覚」が若手に引き継げていない
- 仕上表は整形されているが、特記仕様書と齟齬があることも

## 施工図チェック業務の重要ポイント

### 1. 競合認識

檜山様から明示的にベンチマークとして提示された競合：

- **明かり/燈（Akari/Tomoshibi）**: 図面AIチェッカー。檜山様が画面共有で紹介。現在使っていた
- **セコードテック**: 類似のチェックAI

**差別化の論点**:
> 「ベンチマークにしてこれができないところにやっていくのはプラスかも」

### 2. 既存AIの限界

- 「寸法・記号の間違い指摘」は得意
- ただし**「設計図が正しいかどうか」の判断はできない**
- 設計事務所の図面品質にばらつきがあり、AIの精度が出ない

### 3. 檜山様が本当に欲しいもの（差別化ポイント）

> 「針の大きさとか、そんなレベルのチェックはもうできる。そうじゃなくて、構造的に成立するかどうかの判断ができる方が、経験的に大事」

具体的には：

- **サッシ回り**（最重要）
  - 柱・壁の位置とサッシの取り合い
  - サッシが実際に入るか
  - 防水と構造の両立
- 壁がないところに壁があるべき、柱の大きさの違い等の致命的不整合
- 意匠と構造の整合性（例：意匠図では視界を遮るブレースなし、構造図には同位置にブレース配置）

### 4. 損失規模

- サッシ回りの不整合で手戻り工事が発生すると、**数百万〜数千万円の損失**
- 現場で見つかる頃には手遅れになりがち

## 設計図と施工の視点の違い

檜山様の印象的な発言：

> 「設計のは設計、施工のは施工で視点が違う。設計は『確認用』だが、施工は『現場を作るため』。そこをAIが埋められると価値がある」

**つまり：**
- 単なる図面チェックではなく、「施工できるかどうか」を判断できるAIが求められている
- これは経験の浅い設計者が気付かない部分

## データ提供について

### 合意内容

- **NDA締結後、以下を提供：**
  - 建築案件の設計図面（2〜3物件分）
  - 同案件の**拾い出し数量データ**（AIの出力と比較するための正解データ）

### 檜山様からの補足

> 「図面と拾い数量があれば、プロジェクトを進められる」

- 実際の積算書（金額）は民間案件では出しにくい
- 拾い数量までで十分とのこと

## 技術方針への示唆

| 檜山様の発言 | 技術方針への反映 |
|-------------|----------------|
| 「基本設計段階で用途・スパンから推定したい」 | 過去実績ベースの原単位推定DBが必要 |
| 「PDF・スキャン画像で来ることが多い」 | マルチモーダルLLM必須（OCR+LLMも検討） |
| 「明かり/燈ができないところを」 | 構造チェック特化（サッシ回り等） |
| 「設計と施工の視点が違う」 | 鴻治組のベテラン判断を学習データ化する価値大 |
| 「構造的に成立するかの判断が欲しい」 | 単純ルールベースではなく、LLM推論＋few-shot学習 |

## 結論

- 積算AI・施工図チェックAIの両方に高いニーズあり
- 差別化は **「基本設計段階の概算推定」＋「サッシ回りの構造的成立性チェック」**
- NDA後のデータ提供が合意済みで、PoC実施可能
