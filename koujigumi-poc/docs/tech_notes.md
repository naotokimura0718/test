# 技術メモ

## 技術アプローチの選択

### 結論

**Phase 1: Approach A（Claude API主体）でMVP構築**

精度が不足した場合のみ Approach B（カスタムOCR+LLMハイブリッド）に移行。

### 判断基準

Phase 1 → Phase 2 の移行トリガー：

| 指標 | 移行判断ライン |
|------|--------------|
| 積算精度（数量誤差） | ±10%を3ケース以上で超える |
| 構造チェック Precision | 50%を下回る |
| 応答時間 | 図面1枚あたり30秒を超える |
| コスト | 1件あたりのAPI料金 ¥100を超える |

## Approach A（Phase 1）の技術スタック

### コア

- **LLM**: Anthropic Claude Sonnet 4.6（`claude-sonnet-4-6`）
  - マルチモーダル（画像入力）対応
  - 200K トークンのコンテキスト
  - 日本語・建設用語の精度が高い

### Pythonライブラリ

```
anthropic>=0.40.0        # Claude API公式クライアント
pdf2image>=1.16.0        # PDF → PNG画像への変換
pillow>=10.0.0           # 画像処理

pymupdf>=1.23.0          # PDF読み取り（メタデータ・テキスト抽出）
python-dotenv>=1.0.0     # 環境変数
tenacity>=8.2.0          # APIリトライ
typer>=0.12.0            # CLIフレームワーク
rich>=13.0.0             # CLI出力整形
pytest>=7.4.0            # テスト
pytest-asyncio>=0.23.0
```

### 処理フロー（Approach A）

```
[図面PDF]
    ↓
[pdf2image] PDFを複数ページの画像に変換
    ↓
[分類プロンプト] 各ページが何の図面か分類
    - 平面図 / 立面図 / 断面図
    - 仕上表 / 面積表 / 特記仕様書
    - 配置図 / 構造図 / 設備図
    ↓
[抽出プロンプト] 図面種別に応じた構造化データ抽出
    - 建物概要（用途・構造・階数・延床面積）
    - 仕上仕様（部屋別×部位別）
    - 面積データ（部屋別）
    ↓
[推定プロンプト] 基本設計段階の原単位推定
    - 鴻治組の過去実績DBを参照
    - 用途×構造×スパンから類似物件を検索
    - 原単位の推定値と信頼度を返す
    ↓
[集計] 数量 × 原単位 → 概算見積
    ↓
[構造チェックプロンプト] サッシ回り等の構造的成立性チェック
    - 複数図面を入力として渡す
    - ベテラン判断のfew-shot exampleを含める
    - 指摘事項・信頼度・推奨アクションを返す
    ↓
[出力] JSON形式のレポート
```

## Approach B（Phase 2）への移行条件

精度が不足する場合、以下のアプローチに移行：

### 追加ライブラリ

```
opencv-python-headless>=4.8.0   # 画像処理
layoutparser>=0.3.4             # レイアウト検出
pytesseract>=0.3.10             # OCR（日本語対応）
ultralyticsplus>=0.0.28         # 図面要素検出（YOLO）
```

### 処理フロー（Approach B）

```
[図面PDF]
    ↓
[PDF解析] PyMuPDFでベクター情報・埋め込みテキスト・表を抽出
    ↓
[レイアウト検出] layoutparser で図面領域・表領域を分離
    ↓
[OCR] tesseract/Vision APIで寸法・文字を抽出
    ↓
[構造化] 独自パーサーで図面要素を構造化データに変換
    ↓
[LLM推論] 構造化データをLLMに渡して推論
    （ここで従来のLLM手法とブレンド）
```

### Approach B の検討ポイント

- **CTO松島のCV技術が活きる**：図面要素検出・レイアウト解析
- 精度向上とトレードオフで開発工数大
- 1物件あたりのAPI料金削減（LLMに渡すトークン数が減る）
- 精度の再現性が高い（LLMの確率的挙動の影響を受けにくい）

## プロンプト設計の基本方針

### 原則

1. **構造化出力を強制する**
   - `response_format` でJSON Schema指定
   - Pydanticモデルで型チェック

2. **few-shot examples を活用**
   - 鴻治組様の過去判断を学習データ化
   - 特にサッシ回りチェックは例示が効く

3. **段階的な推論**
   - 「抽出 → 検証 → 推定」のように分離
   - 一度に全部やらせない

4. **信頼度スコアを返させる**
   - AIが確信を持てない箇所は人間判断に回せるように

### プロンプトの例（構造チェック）

```python
SYSTEM_PROMPT = """
あなたは広島の地場ゼネコン「鴻治組」の建築部で40年の経験を持つベテラン施工管理者です。
設計事務所から提出された図面を見て、「施工時に実際に成立するか」を判断します。

特に以下の観点で厳しくチェックしてください：

1. サッシ回りの構造的成立性
   - サッシ開口幅に対する両側の壁厚は十分か
   - 方立・無目の固定が構造的に可能か
   - 防水と構造の両立ができるか

2. 意匠図と構造図の整合性
   - 柱・壁の位置
   - ブレース位置
   - 梁下端とサッシ上端のクリアランス

3. 致命的な不整合
   - 柱の大きさ違い
   - 壁がないところに壁があるべき
   - 部屋名の不一致

指摘する際は、以下を必ず含めてください：
- 場所（階・面・部屋）
- 問題点
- 類似案件での鴻治組の判断
- 推奨アクション
"""
```

## 性能考慮事項

### API呼び出し最適化

- **並列実行**：複数図面を `asyncio.gather` で並列処理
- **キャッシュ**：同じ図面の再解析を避けるため、ファイルハッシュでキャッシュ
- **バッチング**：関連する質問は1回のプロンプトにまとめる

### コスト見積もり

Claude Sonnet 4.6 の料金（参考値）：
- Input: $3 / 1M tokens
- Output: $15 / 1M tokens

1物件あたりの想定トークン数：
- 図面画像10枚 × 1500 tokens = 15,000 tokens（入力）
- 出力 3,000 tokens

1物件あたり約 $0.09（約¥13）

## セキュリティ・コンプライアンス

### NDAデータの取り扱い

- 鴻治組様から受領した図面は `data/drawings/` 配下に格納
- `.gitignore` で除外済み（コミット禁止）
- ログに図面の内容を出力しない（ファイル名のみOK）
- 開発用PCはフルディスク暗号化必須
- PoC終了後、鴻治組様の指示に従って削除

### APIキーの管理

- `.env` ファイルはGitにコミットしない
- 本番環境ではAWS Secrets Manager等を使用予定
- 開発者ごとに個別のAPIキーを発行
